How Direct Lake reads your parquet

What a parquet file is made of, what Power BI does to it on the first click, and why the order of the rows decides what every click after that costs.

the rules and their numbers · source
  1. Power BI never sees your engine. It sees parquet. Spark, a warehouse or DuckDB only matter through the files they leave behind.
  2. The first query pays to load a column. Every query after scans what that load built.
  3. One parquet row group becomes one VertiPaq segment. The writer picks the segment count for you.
  4. Sorted values become runs. VertiPaq stores a run as one (value, count) pair and scans it as one.

1. Direct Lake transcodes, it does not scan files

DuckDB and Spark read the files on every query. Direct Lake reads each column once, converts it into VertiPaq's in-memory format, and answers from memory after that.

That gives three kinds of query, and this project measures each one:

  • cold: the first touch. Pays for the transcode. This is the wait a report user feels on first click.
  • warm: columns already in memory. Pays only for the scan.
  • hot: the same query again, partly answered from caches.

Cold is where layout costs most: across our datasets cold is 3–27× warm. But a live model is mostly warm and hot, so a layout that only helps cold helps less than it looks.

2. What a parquet file looks like inside

A parquet file is cut horizontally into row groups, and each row group stores every column separately as a column chunk. The footer at the end describes all of it.

Two choices made by whoever writes the file decide almost everything below: how many rows go in a row group, and what order the rows are in. The order decides whether the IDs come out as long runs or as noise.

3. One row group becomes one segment

On a cold load, every row group brings its own little dictionary. VertiPaq merges them into one dictionary for the whole column, then rewrites each row group's IDs into a segment.

So the row-group size is a trade, and both ends of it are measured here:

  • Too many, too small and cold load drowns in per-group overhead. DuckDB's default of 122,880 rows per group reached OneLake once: the same table became 1,172 tiny segments instead of about 25.
  • Too few, too big and warm queries lose parallelism: the scan works segment by segment across cores. On the 144M-row AEMO mart, warm time stepped down from ≈5,700 ms to 3,221 ms between 19 and 24 row groups.

Same DuckDB, same notebook, same SQL; only the row-group size differed. Healthy is millions of rows per group (Microsoft says 1–16M). Across our five datasets, more row groups made columns slower to load cold on 5 of 5 and warm queries faster on 4 of 5.

4. The footer decides: swap IDs, or redo everything

If a chunk is dictionary-encoded, VertiPaq can keep the parquet's work and just swap IDs. It only trusts that when the footer says so.

Two ways to land on the slow lane: a writer that never fills in encoding_stats, and a column whose dictionary grew too big so the writer fell back to PLAIN pages part way through. That second one is why a dictionary page size limit is a real setting, not a detail.

5. Sorting turns values into runs

In arrival order, equal values are scattered and every row costs bits. Sorted, they sit next to each other and a whole run costs one pair. VertiPaq keeps the parquet's row order, so it scans those runs too, not just stores them.

payment_type
vendor

Three things to try. Sort by one column and watch its runs collapse to one per value. Add a second key: it gets runs too, but only inside the first key's runs. Swap the order and the winner swaps. That is the whole sort trade-off: the first column takes the best runs, later ones get what is left, and a near-unique column (a timestamp, an amount) cannot form runs at all.

6. Sort the table, or sort each file

A global sort keeps each value in one long run that crosses row groups. Sorting each file on its own restarts every value in every row group.

Global sort: one ORDER BY over the whole table, then cut into row groups
Per-file sort: each file sorted on its own, the way V-Order sorts

Same 48 rows, same four values. Globally sorted, most row groups hold one or two values: few runs, small local dictionaries, little to merge. Sorted per file, every row group holds every value. That is still far better than arrival order, which is why V-Order works, and a per-table sort chosen for the table lands in the same place: in our runs duckrun's sort read at 0.90× V-Ordered Spark's Direct Lake CU, the same within noise.

V-Order is more than a sort. Microsoft describes it as four things: a sort within each file, row-group distribution, dictionary encoding and compression. In Fabric Spark only the readHeavyForPBI profile turns it on; it lowered cold load on 5 of 5 of our datasets.

7. What does not matter

File count and file size. Direct Lake loads whole columns and does no file or row-group skipping, so neither ever separated writers in the cost data. The one rule: never cap a file below one row group's bytes, or the writer has to cut the row group short.
