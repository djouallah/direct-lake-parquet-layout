Databricks

Eleven lines of cluster config plus one CLUSTER BY per fact table, and a Databricks-written table queries in Direct Lake within 4% of Fabric's own V-Ordered layout.

Measured on TPC-DS SF100 and SF1000 with Microsoft's own Direct Lake benchmark protocol: the DAX from the paper Modern Power BI Architecture Choices for Reporting on Azure Databricks, 20 concurrent readers. Full repo: djouallah/parquet_layout_vertipaq_spark.

Step 1: the cluster config, the same on every cluster that writes these tables

spark.sql.files.maxRecordsPerFile                                      6000000     # default 0 = no limit
spark.hadoop.parquet.block.size                                        2147483648  # default 128 MB
spark.databricks.delta.optimizeWrite.enabled                           true        # default false
spark.databricks.delta.optimizeWrite.binSize                           4096        # default 512

spark.hadoop.parquet.page.row.count.limit                              16000000    # default 20000
spark.hadoop.parquet.page.size                                         67108864    # default 1 MB
spark.hadoop.parquet.dictionary.page.size                              67108864    # default 1 MB
spark.hadoop.parquet.enable.dictionary                                 true        # default true

spark.databricks.delta.properties.defaults.checkpointPolicy            classic     # default v2 with CLUSTER BY
spark.databricks.delta.properties.defaults.autoOptimize.optimizeWrite  true
spark.databricks.delta.properties.defaults.autoOptimize.autoCompact    false

maxRecordsPerFile is the segment: one file, one row group, 6M rows, whatever the table's width. The page and dictionary sizes keep wide columns dictionary-encoded. And three cluster settings that are not optional:

  • Photon off (runtime_engine: STANDARD). Photon's writer ignores every parquet.* key.
  • Latest runtime (measured on DBR 19). Older runtimes accept parquet keys they do not implement, silently.
  • Predictive optimization off: ALTER SCHEMA … DISABLE PREDICTIVE OPTIMIZATION. Anything that rewrites the files without this config undoes the layout.

Step 2: per fact table, CLUSTER BY the column the reports filter

fq  = "catalog.schema.store_sales"
key = "ss_sold_date_sk"          # the ONE column the reports filter on

df.limit(0).write.format("delta").saveAsTable(fq)                                    # empty table, schema only
spark.sql(f"ALTER TABLE {fq} SET TBLPROPERTIES ('delta.checkpointPolicy' = 'classic')")
spark.sql(f"ALTER TABLE {fq} CLUSTER BY ({key})")
df.write.format("delta").mode("append").saveAsTable(fq)                              # the write, unchanged

Dimensions get a plain saveAsTable. What breaks it, each one measured:

  • One key only. Two keys become a Hilbert curve, which orders no single column.
  • checkpointPolicy = classic before the key exists. Direct Lake cannot read a v2 checkpoint.
  • No df.orderBy(key). Optimized Writes throws the sort away; CLUSTER BY is how an order reaches the file.
  • No OPTIMIZE from compute without the config, and SQL warehouses are that compute.
  • Verify per file. Clustering on write is size-gated and silent when it skips: check min and max of the key in each file.

delta-rs (Python, Rust, duckrun)

delta-rs keeps dictionaries everywhere once you raise one limit. The row-group size and the sort are yours to set.

This is the profile duckrun ships as its default, each value tuned against a Spark V-Order reference with DAX timings as the signal.

from deltalake import write_deltalake, WriterProperties, ColumnProperties

wp = WriterProperties(
    compression="SNAPPY",                     # transcoding is decode-bound
    max_row_group_size=4_000_000,             # rule 1, in ROWS: mid-band of the measured 2-6M
    dictionary_page_size_limit=32 * 1024**2,  # rule 2: THE knob; the ~1 MB default drops wide columns to PLAIN
    data_page_size_limit=1024**2,
    data_page_row_count_limit=1_000_000,      # stops a very compressible column becoming one giant page
    statistics_truncate_length=64,
    default_column_properties=ColumnProperties(
        dictionary_enabled=True, statistics_enabled="CHUNK"),
)

# rule 3: `table` must already be sorted by the filter column; no writer setting sorts for you
write_deltalake(path, table, writer_properties=wp,
                target_file_size=256 * 1024**2)   # a row group cannot span files: keep this above one group's bytes
  • The dictionary limit is the one to remember. One 144M-row DECIMAL(18,4) column measured 618.6 MB as PLAIN against 423.1 MB dictionary-encoded.
  • Raising it costs the writer memory, not the reader: an 18M-row merge at a 128 MB limit hit ~25 GB, at 8 MB ~4 GB.
  • delta-rs already writes encoding_stats, so its dictionaries take the fast remap path.

DuckDB

Power BI reads a lakehouse table, not a loose parquet file, so what matters is which table format DuckDB writes, and whether that path lets you set the parquet layout.

DuckDB → Delta: a dead end for layout

DuckDB's delta extension writes Delta, but it exposes none of the parquet settings: no row-group size, no dictionary limit, no sort it keeps. Whatever its defaults produce is what Power BI gets, and there is no knob to fix it.

DuckDB → Iceberg

DuckDB's iceberg extension writes through an Iceberg REST catalog, OneLake's included, and OneLake exposes the table to Direct Lake. Here the geometry can be set, through Iceberg table properties, set when the table is created.

ATTACH '<warehouse>' AS lake (TYPE iceberg, ENDPOINT '<rest endpoint>', TOKEN '<token>');

CREATE TABLE lake.dbo.fct_sales WITH (
    'write.parquet.row-group-size'       = '4000000',      -- rows: DuckDB's own key
    'write.parquet.row-group-size-bytes' = '1073741824',   -- 1 GiB: otherwise a 128 MB cap closes the group first
    'write.target-file-size-bytes'       = '1073741824',   -- 1 GiB: must be at least the row-group budget, see below
    'write.parquet.page-size-bytes'      = '1048576'       -- 1 MB pages; the default is one ~100 MB page per column chunk
) AS
SELECT * FROM staging_sales ORDER BY order_date;           -- the sort: ORDER BY in the CTAS
  • The rule these settings give you, on any table: a row group closes at 4M rows or 1 GiB of uncompressed data, whichever comes first, and a file closes at the first row-group boundary past 1 GiB. Files land at about 1 GB; tables with wide rows get row groups under 4M rather than bigger files.
  • The row count alone does nothing on a wide table. The writer also closes a row group at 128 MB uncompressed by default, which on a 17-column table is ~813K rows. Raise the byte budget with it, as above.
  • The file size caps the row group. The writer never lets the row-group byte budget exceed the file target, so a small file target (say 128 MB) quietly brings back small row groups. Keep the two equal.
  • One row group per file is not possible yet. write.parquet.row-groups-per-file is accepted but does nothing (duckdb-iceberg#1606), so large row groups always come in files of several row groups.
  • Properties must be set at create time. Setting them after the first write changes nothing already written.
  • Later inserts: ALTER TABLE … SET SORTED BY (order_date) makes every insert honour the sort.
  • The dictionary is not reachable yet. Neither dictionary_size_limit nor the parquet version is mapped to a table property (write.parquet.dict-size-bytes is a different knob and makes it worse). Measured here, a wide numeric column still fell to PLAIN on 10 of 53 chunks.
  • Page size needs a recent extension. write.parquet.page-size-bytes is mapped since duckdb-iceberg#1365; an older one stores the property and ignores it. Check the page count in the file footer.
  • Check what you got. Read the row-group count and file count from the footer after the write; settings that are accepted and ignored look exactly like settings that worked.
  • Use a recent DuckDB. The footer declaration (duckdb#24957) is in the pre-release only; on this repo it halved cold load and cut read CU 2.5× on its own.

Or let duckrun do it

duckrun is a helper project that makes this easy: your SQL still runs in DuckDB, but the Delta table is written by delta-rs with the delta-rs profile already applied (millions of rows per row group, dictionaries kept and declared). The only decision left is the sort.

import duckrun

con = duckrun.connect(
    "abfss://<workspace>@onelake.dfs.fabric.microsoft.com/<lakehouse>.Lakehouse/Tables/dbo",
    read_only=False)

con.sql("""
    CREATE OR REPLACE TABLE fct_sales SORTED BY (order_date) AS   -- or SORTED BY AUTO
    SELECT * FROM staging_sales
""")

In dbt it is the duckrun adapter and one config line, sort_by='auto'. Its global sort read at 0.90× V-Ordered Spark's Direct Lake CU in this repo.
