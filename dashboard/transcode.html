What a reader does with the file

Whatever the format on disk, an engine translates it into its in-memory format first; in Power BI that step is called transcoding. Direct Lake keeps the result in memory, so the file's layout is paid for mostly on first touch. Three choices the writer made decide how much work it is: how many row groups, whether each column is dictionary-encoded, and what order the rows are in.

Row groups become segments, one to one

The first time a query touches a column (the cold load), every row group brings its own little dictionary. VertiPaq merges them into one dictionary for the whole column, then turns each row group into one segment. Row groups are never merged or split on the way in, so the writer chose your segments.

Segments vs threads: the warm scan wants enough of them

A warm query scans segments in parallel, one per thread at a time. With fewer segments than threads some threads sit idle, however big each segment is.

8 threads is a number picked for the demo. How many threads Direct Lake's scan gets is not documented.

Microsoft lays out row groups to match the capacity's cores and warns that uneven row-group sizes unbalance the scan. Measured on the 144M-row AEMO mart: warm query time stepped down from ≈5,700 ms at 19 segments to 3,221 ms at 24, and 72 segments bought nothing over 24.

A strict "segments ÷ threads" cost model was tested with a deliberate 8-segment run and did not hold, consistent with fetching and transcoding overlapping the scan. The thread count itself is not documented, so the step from 19 to 24 segments is the only measured hint of where it sits.

Cold, warm, hot

The merge and the ID swap happen once per column. After that the column stays in VertiPaq's memory and later queries only scan it. A query's cost depends on whether its columns are already there.

the query:
this query is
parquet chunks read from OneLake
dictionaries merged
segments scanned

That gives three kinds of query, and this project measures each one:

  • cold: the first touch. Pays for the transcode.
  • warm: columns already in memory. Pays only for the scan.
  • hot: the same query again, partly answered from caches.

Two things send a column back to cold: the table is rewritten (new data, an OPTIMIZE: a reframe), or the capacity runs short of memory and unloads segments.

Measured in this project, a cold pass of the query suite took 3–27× its warm pass, depending on the dataset. So the layout is paid for mostly once, at the cold load, and that is where the read CU goes. One part keeps paying after: the row order survives into memory (Parquet · Sorting).

A caution that holds for every number in this tour: a live model transcodes once per reframe or memory eviction and then serves mostly warm and hot traffic. This benchmark deploys a fresh model every run, so cold is fully represented: read the cold numbers as the price of first touch.

Recap

What Direct Lake does not do

Direct Lake does no statistics-based file or row-group skipping when it loads a column. It loads the whole column, so file count and file size are not levers.

  • File count never separated writers in the read CU data: the Warehouse ships 78 files and sits mid-pack. See the file count card.
  • A smaller file is not a faster one. A sort key that cut the file 30% bought no query time. Bytes on disk follow from dictionary and sort.
  • The one file-size trap: delta-rs truncates the row group in progress at the file-size cap (groups at 0.43× their declared rows). That makes segments small and uneven, which is exactly the unbalanced scan of the previous sections. Keep the file cap above one row group's bytes.
  • Joins load more than you asked for. A cold query that crosses a relationship builds a join index, which loads the key columns' dictionaries and the dimension key's segments. A star-schema cold query pays for the dimension too.
  • Memory is not forever. Under memory pressure the engine unloads segments and join indexes and rebuilds them on the next query that needs them: back to cold.
