AEMO, 144M rows, Direct Lake. Median of three runs (34128354827, 34735629895, 35836350582) against two (38998148550, 39024032584). The live number is on the dictionary card; why it happens: Transcoding · ID swap.

So optimise the file for the read, not the write. A table is written once and then read for days, sometimes months, by every report that uses it. Reading is what users wait on (in my experience they notice 500 ms), and it costs capacity every time.

Fabric's answer is V-Order, and it is three things: dictionary encoding, row groups of millions of rows, and a sort that turns equal values into long runs. If your writer has it (Fabric Spark, Fabric Warehouse), turn it on: the write costs a little more and the read pays it back. If your writer does not (delta-rs, DuckDB, Databricks), you can set the same three things yourself.

The core issue is not technical. Whoever writes the table sees how long the pipeline took; nobody shows them what it costs to read.

Two formats: on disk, and in memory

Every engine deals with two formats: the format on disk, and the format in memory where it actually computes.

the format on disk is:

The two formats are very close. Parquet and VertiPaq both store a table column by column, encode a column as a dictionary plus small IDs, and cut it into pieces (row groups in parquet, segments in VertiPaq). The main difference: parquet keeps a separate dictionary in every row group, VertiPaq keeps one dictionary for the whole column.

How much work the translation is depends on how the file was written.

VertiPaq stores a column as a dictionary plus small IDs, and a run of equal IDs as one pair, scanned as one. The more a column repeats, and the closer together the repeats sit, the less there is to hold in memory and to scan.

Direct Lake keeps the row order of the parquet it reads, so the repetition only pays off if the writer put equal values next to each other. TPC-H, TPC-DS and SSB generate uniform data and hide this; every dataset here is real.

Fabric Spark and Fabric Warehouse are the two writers that have V-Order. delta-rs and DuckDB do not, and neither does Databricks; they have to set its three parts themselves.

V-Order is three things, and they decide the read cost whoever wrote the file:

  1. Dictionary encoding on every column, declared in the footer. Parquet · Transcoding
  2. Sort order that turns equal values into long runs. Parquet · Transcoding
  3. Row groups of millions of rows each. Parquet · Transcoding
