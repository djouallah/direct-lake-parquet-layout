Same rows, different files, different bill

Why the program that writes a Delta table decides what Power BI pays to read it, and the three things any writer can do about it.

For decades a database read only files it had written itself. The lakehouse broke that: one engine writes the file, another reads it. The reader now has to translate a file it did not design, and how much work that is was decided by the writer.

Before: the engine owned the format

SQL Server, a Power BI import model, Analysis Services: each one writes its own storage format and reads it back exactly as written. The writer and the reader are the same program, so the bytes are always in the shape the reader wants.

That arrangement has one big advantage and one big cost.

  • The advantage: the format is tuned for exactly one reader. An import-mode Power BI model builds its VertiPaq segments at refresh, sorted and dictionary-encoded the way VertiPaq likes them, and every query reads them as they are.
  • The cost: the data is locked in. Every other tool that wants it needs its own copy, its own load, its own refresh.

Keep the import model in mind: it is the same VertiPaq engine Direct Lake uses. What changes in Direct Lake is only who wrote the file.

Then: the lakehouse

Open table formats (Delta Lake or Iceberg, both made of parquet files plus a log) put one copy of the data in OneLake that any engine can write and any engine can read. The format belongs to nobody, so no reader gets a file shaped for it.

Pick a reader. Every path out of OneLake goes through a decode step.

What you get is one copy and a free choice of engine. What you give up is that the file is no longer written for its reader. A writer's defaults are tuned for the writer: write fast, use little memory, make files of a convenient size. Nothing in the format makes it think about who reads next.

The price: every reader decodes

No engine computes on parquet bytes as they sit in the file. DuckDB turns them into its vectors, Spark into its columnar batches, VertiPaq into segments. That translation is real work, and three choices the writer made decide how much.

Pay on every query, or pay once

Most engines decode the parquet again on every query. Direct Lake decodes a column the first time a query needs it, keeps the result in memory, and answers later queries from that copy. That one difference is where cold, warm and hot come from.

Measured in this project, the gap between first and later visits shows the difference:

storage modecold ÷ warm, range across the datasets
Direct Lake3–27×
DirectQuery1.6–3.3×

So in Direct Lake the layout is paid for mostly once, at the cold load, and that is where the read CU goes. One part of it keeps paying after: the row order survives into memory, so a sorted table is also cheaper to scan warm. DirectQuery pays for the file on every query; its read CU against Direct Lake is on the DirectQuery card.

A caution that holds for every number in this tour: a live model transcodes once per reframe or memory eviction and then serves mostly warm and hot traffic. This benchmark deploys a fresh model every run, so cold is fully represented: read the cold numbers as the price of first touch.

This is not a ranking of writers. The finding is that three properties of the file decide the read cost, and any writer that gets them right reads cheaply:

  1. Dictionary encoding on every column, declared in the footer. Parquet · Transcoding
  2. Sort order that turns equal values into long runs. Parquet · Transcoding
  3. Row groups of millions of rows each. Parquet · Transcoding
