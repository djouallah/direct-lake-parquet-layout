Databricks

これらのライターには V-Order のスイッチがありません。そのため、このページの各レシピでは V-Order を構成する 3 つの要素、すなわち辞書エンコーディング、行グループのサイズ、ランを短くするソートを手作業で設定します。

測定は TPC-DS SF100 と SF1000 で、Microsoft 自身の Direct Lake ベンチマーク手順に従って行いました。DAX は論文 Modern Power BI Architecture Choices for Reporting on Azure Databricks のもので、同時読み取りユーザーは 20 です。リポジトリ全体: djouallah/parquet_layout_vertipaq_spark。

SF1000 では、設定のみの場合はまったくウォームアップしなくなります（3 回の実行で 814 → 875 → 1,045 秒と、 回を追うごとに遅くなる）。一方、ソート済みのレイアウトはどれも安定します。これが CLUSTER BY を 1 つ入れる理由です。

ステップ 1: クラスター設定（これらのテーブルを書き込むすべてのクラスターで同一にする）

spark.sql.files.maxRecordsPerFile                                      6000000     # 既定値 0 = 上限なし
spark.hadoop.parquet.block.size                                        2147483648  # 既定値 128 MB
spark.databricks.delta.optimizeWrite.enabled                           true        # 既定値 false
spark.databricks.delta.optimizeWrite.binSize                           4096        # 既定値 512

spark.hadoop.parquet.page.row.count.limit                              16000000    # 既定値 20000
spark.hadoop.parquet.page.size                                         67108864    # 既定値 1 MB
spark.hadoop.parquet.dictionary.page.size                              67108864    # 既定値 1 MB
spark.hadoop.parquet.enable.dictionary                                 true        # 既定値 true

spark.databricks.delta.properties.defaults.checkpointPolicy            classic     # CLUSTER BY 使用時の既定値は v2
spark.databricks.delta.properties.defaults.autoOptimize.optimizeWrite  true
spark.databricks.delta.properties.defaults.autoOptimize.autoCompact    false

maxRecordsPerFile がセグメントを決めます。テーブルの列数にかかわらず、1 ファイル = 1 行グループ = 600 万行です。 ページサイズと辞書サイズの設定により、幅の広い列でも辞書エンコーディングが維持されます。さらに、 省略できないクラスター設定が 3 つあります。

  • Photon をオフにする（runtime_engine: STANDARD）。Photon のライターは parquet.* キーをすべて無視します。
  • 最新のランタイムを使う（DBR 19 で測定）。古いランタイムは、実装していない parquet キーも黙って受け付けます。
  • 予測最適化をオフにする: ALTER SCHEMA … DISABLE PREDICTIVE OPTIMIZATION。この設定なしでファイルを書き直す処理は、すべてレイアウトを元に戻してしまいます。

ステップ 2: ファクトテーブルごとに、レポートがフィルターする列で CLUSTER BY

fq  = "catalog.schema.store_sales"
key = "ss_sold_date_sk"          # レポートがフィルターする唯一の列

df.limit(0).write.format("delta").saveAsTable(fq)                                    # 空のテーブル、スキーマのみ
spark.sql(f"ALTER TABLE {fq} SET TBLPROPERTIES ('delta.checkpointPolicy' = 'classic')")
spark.sql(f"ALTER TABLE {fq} CLUSTER BY ({key})")
df.write.format("delta").mode("append").saveAsTable(fq)                              # 書き込み自体は変更なし

ディメンションは通常の saveAsTable で構いません。これを崩す要因は以下のとおりで、いずれも測定で確認しています。

  • キーは 1 つだけ。キーを 2 つにすると Hilbert 曲線になり、どの列も単独では順序付けられません。
  • キーを設定する前に checkpointPolicy = classic にする。Direct Lake は v2 チェックポイントを読み取れません。
  • df.orderBy(key) は使わない。Optimized Writes がそのソートを捨ててしまいます。ファイルに順序を届ける手段は CLUSTER BY です。
  • この設定のないコンピューティングから OPTIMIZE を実行しない。SQL ウェアハウスもそうしたコンピューティングに該当します。
  • ファイルごとに検証する。書き込み時のクラスタリングはサイズ条件付きで、スキップしても何も通知されません。各ファイルでキーの最小値と最大値を確認してください。

Claude Code をお使いですか？このレシピはスキルとして提供されているため、アシスタントが orderBy や repartition に頼らず、測定どおりに適用します: /plugin marketplace add djouallah/parquet_layout_vertipaq_spark。

delta-rs（Python、Rust、duckrun）

これは duckrun が既定として提供しているプロファイルです。 各値は、Spark の V-Order を基準とし、DAX の所要時間を指標にして調整したものです。

from deltalake import write_deltalake, WriterProperties, ColumnProperties

wp = WriterProperties(
    compression="SNAPPY",                     # トランスコードはデコード律速
    max_row_group_size=4_000_000,             # ルール 1（行数で指定）: 測定上の 2-6M の中央
    dictionary_page_size_limit=32 * 1024**2,  # ルール 2: 最重要の設定。約 1 MB の既定値では幅の広い列が PLAIN に落ちる
    data_page_size_limit=1024**2,
    data_page_row_count_limit=1_000_000,      # 圧縮率の高い列が巨大な 1 ページになるのを防ぐ
    statistics_truncate_length=64,
    default_column_properties=ColumnProperties(
        dictionary_enabled=True, statistics_enabled="CHUNK"),
)

# ルール 3: `table` はフィルター列で事前にソートしておくこと。ライターの設定ではソートされない
write_deltalake(path, table, writer_properties=wp,
                target_file_size=256 * 1024**2)   # 行グループはファイルをまたげない: 1 グループのバイト数より大きく保つ
  • 覚えておくべきは辞書の上限です。1 億 4,400 万行の DECIMAL(18,4) 列 1 つで、 PLAIN では 618.6 MB、辞書エンコーディングでは 423.1 MB でした。
  • 上限を上げるとライターのメモリを消費します（リーダー側ではありません）。1,800 万行のマージで、 上限 128 MB では約 25 GB、8 MB では約 4 GB に達しました。
  • delta-rs はすでに encoding_stats を書き込みます。そのため、その辞書は高速なリマップ経路に乗ります。

DuckDB

DuckDB → Delta: レイアウトの観点では行き止まり

DuckDB の delta 拡張は Delta を書き込めますが、parquet の設定を一切公開していません。行グループのサイズも、 辞書の上限も、維持されるソートもありません。既定値で生成されたものがそのまま Power BI に渡り、 それを直す設定項目はありません。

DuckDB → Iceberg

DuckDB の iceberg 拡張は、OneLake を含む Iceberg REST カタログを通じて書き込みます。OneLake は そのテーブルを Direct Lake に公開します。こちらではジオメトリを設定できます。設定は テーブル作成時に指定する Iceberg テーブルプロパティで行います。

ATTACH '<warehouse>' AS lake (TYPE iceberg, ENDPOINT '<rest endpoint>', TOKEN '<token>');

CREATE TABLE lake.dbo.fct_sales WITH (
    'write.parquet.row-group-size'       = '4000000',      -- rows: DuckDB's own key
    'write.parquet.row-group-size-bytes' = '1073741824',   -- 1 GiB: otherwise a 128 MB cap closes the group first
    'write.target-file-size-bytes'       = '1073741824',   -- 1 GiB: must be at least the row-group budget, see below
    'write.parquet.page-size-bytes'      = '1048576'       -- 1 MB pages; the default is one ~100 MB page per column chunk
) AS
SELECT * FROM staging_sales ORDER BY order_date;           -- the sort: ORDER BY in the CTAS
  • これらの設定がもたらすルール（どのテーブルでも同じ）: 行グループは 400 万行または非圧縮データ 1 GiB の いずれか早い方で閉じ、ファイルは 1 GiB を超えた後の最初の行グループ境界で閉じます。ファイルは約 1 GB になり、 行の幅が広いテーブルでは、ファイルが大きくなるのではなく行グループが 400 万行未満になります。
  • 幅の広いテーブルでは、行数だけを設定しても効果はありません。ライターは既定で 非圧縮で 128 MB に達した時点でも行グループを閉じ、17 列のテーブルではそれが約 81.3 万行に相当します。 上記のように、バイト上限も合わせて引き上げてください。
  • ファイルサイズが行グループの上限になります。ライターは行グループのバイト上限がファイルの目標サイズを 超えることを許さないため、ファイルの目標を小さく（たとえば 128 MB）すると、気づかないうちに小さな行グループに戻ります。両者は同じ値にしてください。
  • 1 ファイル 1 行グループには、まだできません。write.parquet.row-groups-per-file は 受け付けられますが何もしません（duckdb-iceberg#1606）。 そのため、大きな行グループは常に複数の行グループを持つファイルになります。
  • プロパティは作成時に設定する必要があります。最初の書き込みの後で設定しても、書き込み済みのデータは何も変わりません。
  • 以降の INSERT: ALTER TABLE … SET SORTED BY (order_date) を設定すると、すべての INSERT がソートを守ります。
  • 辞書はまだ制御できません。dictionary_size_limit も parquet の バージョンもテーブルプロパティに対応付けられていません（write.parquet.dict-size-bytes は別の設定で、 かえって悪化します）。ここでの測定では、幅の広い数値列が 53 チャンク中 10 チャンクで依然として PLAIN に落ちました。
  • ページサイズには新しい拡張が必要です。write.parquet.page-size-bytes は duckdb-iceberg#1365 以降で対応付けられています。古い拡張では プロパティは保存されますが無視されます。ファイルのフッターでページ数を確認してください。
  • 結果を確認する。書き込み後に、フッターから行グループ数とファイル数を読み取ってください。 受け付けられたのに無視された設定は、効いた設定とまったく同じに見えます。
  • 新しい DuckDB を使う。フッターでの宣言（duckdb#24957）は プレリリース版にしかありません。このリポジトリでは、それだけでコールドロードが半分になり、読み取り CU が 2.5 分の 1 になりました。

または duckrun に任せる

duckrun は、これを簡単にする補助プロジェクトです。 SQL はこれまでどおり DuckDB で実行されますが、Delta テーブルは delta-rs のプロファイルを適用済みの delta-rs で書き込まれます（行グループあたり数百万行、 辞書は維持・宣言済み）。残る判断はソートだけです。

import duckrun

con = duckrun.connect(
    "abfss://<workspace>@onelake.dfs.fabric.microsoft.com/<lakehouse>.Lakehouse/Tables/dbo",
    read_only=False)

con.sql("""
    CREATE OR REPLACE TABLE fct_sales SORTED BY (order_date) AS   -- or SORTED BY AUTO
    SELECT * FROM staging_sales
""")

dbt では duckrun アダプターを使い、設定 1 行 sort_by='auto' で済みます。このリポジトリでは、 そのグローバルソートの Direct Lake CU は、V-Order を適用した Spark の 0.90 倍でした。データセットごとの数値は ライターの比較にあります。

ファイルの確認: フッターを読み戻す

ライターは設定を無視しても何も知らせません。このプロジェクトでも 2 回、宣言した設定がファイルに反映されておらず、 それを示したのはフッターだけでした。DuckDB 2.0 の parquet_metadata() は、 encoding_stats を含めてフッターを表示します。

SELECT row_group_id, row_group_num_rows, path_in_schema,
       encodings, encoding_stats, total_compressed_size
FROM parquet_metadata('abfss://<workspace>@onelake.dfs.fabric.microsoft.com/<lakehouse>/Tables/<table>/*.parquet')
ORDER BY path_in_schema, row_group_id;

どのライターで書いたテーブルでも、確認するポイントは次のとおりです。

  1. 行グループ: row_group_num_rows が数百万行規模で、かつ均等であること。
  2. 辞書: すべてのチャンクに encoding_stats があり、PLAIN のデータページがないこと。
  3. ソート: グローバルソートの後は、先頭のソートキーの最小値と最大値が行グループごとに 段階的に増加すること。V-Order のようなファイル単位のソートでは範囲が重なりますが、それは想定どおりです。

古い DuckDB リリースや pyarrow は encoding_stats を公開していません。そのため、このプロジェクトの stats.py はフッターを自前でデコードしています。各フィールドの意味: Parquet · フッター。
