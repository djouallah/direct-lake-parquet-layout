1 つのファイルの内部

parquet ファイルは横方向に行グループへ分割され、各行グループはすべての列を列チャンクとして個別に格納します。 末尾のフッターが、その全体を記述しています。

任意の列チャンク、またはフッターをクリックすると、中身を表示します。

このプロジェクトの AEMO マートの形状です: 1 億 4,400 万行、5 列、date、次に time でソート。 ファイルに格納されているのは値ではなく ID で、辞書がそれを値に戻します。

date と DUID を比べてください。同じファイル、同じ行グループなのに、一方は少数の長いランで、 もう一方はノイズです。この違いを生んだのはライターの行の順序です。ライターが選べる 3 つのこと（行グループのサイズ、エンコーディング、行の順序）のうち、 列がメモリに載った後もクエリに影響し続けるのはこれだけです。

エンコーディング: 値そのものか、辞書への ID か

列チャンクには、値そのもの（PLAIN）を格納するか、異なる値を 1 回ずつ並べた辞書と、 行ごとの小さな整数 ID を格納します。ソートされた ID は、さらにランへとまとまります。

データページ
このサンプルチャンクのバイト数

  • 値が繰り返す箇所では、辞書エンコーディングのほうが小さくなります。実際の 1 列 （1 億 4,400 万行の DECIMAL(18,4)）での測定値: PLAIN の 618.6 MB に対し、辞書エンコーディングでは 423.1 MB。
  • Power BI が再利用できるのも辞書です。VertiPaq 自体が辞書エンコーディングを用いるため、parquet の 辞書はロード時に作り直さず、そのまま採用できます（トランスコード: ID の差し替えか再構築か）。
  • ライターは辞書を黙って捨てます。各ライターには辞書サイズの上限があり、それを超えるとチャンクの残りは PLAIN にフォールバックします。このプロジェクトでは、OSS プロファイルの Spark ライターと DuckDB 自身の parquet ライターが、最も幅の広い列で辞書を捨てていました。この設定の名前はライターごとに異なります: delta-rs では dictionary_page_size_limit（バイト数）、 DuckDB では DICTIONARY_SIZE_LIMIT（異なる値の数）。

このサンプルでは、値 1 つを 4 バイト、ID 1 つを 2 ビット、ラン 1 つを 2 バイトとして数えています。実際のページには ヘッダーと圧縮が加わりますが、4 つの方式の大小関係は変わりません。

フッター: ファイルの目次

リーダーは最初にフッターを開きます。フッターには、スキーマ、各行グループの行数、各チャンクの開始位置、 チャンクごとの min/max、そして各チャンクのページがどのエンコーディングを使っているかが格納されています。

1 チャンク分のフッターエントリ:

重要なフィールドは encoding_stats です。ページ種別ごとに、どのエンコーディングのページがいくつあるかを示します。 ページをデコードせずにチャンク全体が辞書エンコーディングであることを証明できる唯一の構造であり、 Power BI が ID を差し替えるか列を再構築するかは、これで決まります。それぞれの場合にリーダーが何をし、 どれだけのコストがかかったか: トランスコード · ID の差し替え。

フッターを読み戻すクエリ: サードパーティのライター · ファイルを 確認する。

行グループ: 決めるのはライター、望むサイズになることはまれ

ライターは、行数かバイト予算のどちらか先に達した時点で行グループを閉じます。 ライブラリの既定値はリーダーではなくライターのメモリに合わせたサイズで、DuckDB の既定値は 122,880 行です。 Power BI が求めるのは数百万行です。

ソート

ソートで値がランになる

ソートすると等しい値が隣り合い、ラン全体を、行ごとの 1 エントリではなく 1 組の値として格納できます。 Direct Lake は読み込んだ parquet の行の順序を保持するので、ライターが作ったランが、 その後のすべてのクエリがスキャンするランになります。

ラン数の合計

V-Order は自動のソートです。すべての列を同時にソート対象とし、最も繰り返しの多い列から並べるため、 ランを作れる列はすべてランになり、誰もキーを指定する必要がありません。

手動のソートは、指定した列だけを並べます。実際のデータは組み合わせで繰り返す（同じ種類の 乗車が何度も現れる）ため、指定しなかった列は到着時と同じくばらばらのままです。

グローバルソートか、ファイルごとのソートか

グローバルソートはテーブル全体を並べるため、各値は行グループやファイルをまたぐ 1 本の長いランになります。 ファイルごとのソート（V-Order が行うもの）は各ファイル内の行を並べるため、どの値もすべての行グループで 改めて始まります。

同じ 48 行を、次の形で書き込み:
スキャンするラン数
マージするローカル辞書のエントリ数

圧縮の点では両者に大差はなく、どちらも到着順よりはるかに優れています。

実践的なアドバイス: 箱の中の箱

複数列でのソートは、箱の中の箱です。第 1 キーがテーブルを少数の大きな箱に分け、その列に長いランを 与えます。第 2 キーはそれぞれの箱の中だけで並べ、第 3 キーは第 2 キーが残した箱の中だけで並べる、 というように続きます。

  • 最も重要なのは第 1 列、第 2 列は少し、それ以降は効果が急速に小さくなります。 4 つ目、5 つ目のキーを加えると、書き込みのたびにソート時間がかかるのに、得られるものはほぼありません。
  • そのため、手動でソートするなら第 1 キーを慎重に選んでください。長いランが保証されるのは その列だけです。
  • 迷ったら日付を使いましょう。ほぼすべてのレポートが日付でフィルターしますし、データはたいてい もともと日付順に到着するうえ、期待を裏切ることはまずありません。
