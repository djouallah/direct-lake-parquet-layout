同じテーブルで、読み取りコストが 2.5 倍

同じライターが同じテーブルを 2 回書き出しました。行も行グループも同じで、ディスク上のバイト数も同じです。 ただし一方はファイルのフッターで列が辞書エンコーディングされていることを宣言し、もう一方は何も宣言していません。

テーブルを書き出したライター:
Power BI 読み取り CU
コールドロード（クエリスイート全体）

AEMO、1 億 4,400 万行、Direct Lake。DuckDB による Iceberg 書き込みを duckdb#24957 の前後で比較：各 1 回の実行（32444969823、 33700004854）、行グループはどちらも 53、サイズはどちらも 1,129 MB。最新の数値は 辞書カードに、その理由は トランスコード · ID の置き換えにあります。

だからこそ、ファイルは書き込みではなく読み取りに合わせて最適化すべきです。テーブルは一度書き出されたあと、 それを使うすべてのレポートから数日、ときには数か月にわたって読まれ続けます。ユーザーが待たされるのは読み取りであり （私の経験では 500 ms の差でも気づかれます）、読み取りのたびに容量を消費します。

Fabric の答えは V-Order です。その中身は 3 つ：辞書エンコーディング、数百万行単位の行グループ、 そして同じ値を長いランにまとめるソートです。お使いのライターが V-Order に対応しているなら（Fabric Spark、 Fabric Warehouse）、有効にしてください。書き込みのコストは少し増えますが、読み取りで回収できます。 対応していないライター（delta-rs、DuckDB、Databricks）でも、同じ 3 つを自分で設定できます。

本当の問題は技術ではありません。テーブルを書き出す側にはパイプラインの所要時間は見えても、 読み取りにいくらかかるかは誰も見せてくれないのです。

2 つのフォーマット：ディスク上とメモリ上

どのエンジンも 2 つのフォーマットを扱います。ディスク上のフォーマットと、実際に計算を行うメモリ上のフォーマットです。

ディスク上のフォーマット:

2 つのフォーマットはよく似ています。parquet も VertiPaq もテーブルを列ごとに格納し、列を辞書と小さな ID で エンコードし、それを分割して持ちます（parquet では行グループ、VertiPaq ではセグメント）。主な違いは、parquet が 行グループごとに別々の辞書を持つのに対し、VertiPaq は列全体で 1 つの辞書を持つ点です。

変換の手間がどれだけかかるかは、ファイルがどう書かれたかで決まります。

測定内容

同じ行を異なるライターで書き出し、読み取りの請求を比べました。実在する 5 つの公開データセットについて、4 つのエンジン （Spark は V-Order あり・なしの 2 通り）が同じ行を出力し、データセットごとに 1 つのセマンティックモデルと 1 つの DAX スイートを用意して、各読み取りセッションで課金された容量ユニット（CU）を測定しています。

V-Order を持つライターは Fabric Spark と Fabric Warehouse の 2 つです。delta-rs と DuckDB、そして Databricks は V-Order を持たないため、その 3 つの要素を自分で設定する必要があります。

V-Order は 3 つの要素からなり、誰がファイルを書いたかにかかわらず、それが読み取りコストを決めます：

  1. 全列に辞書エンコーディングを適用し、フッターで宣言する。 Parquet · トランスコード
  2. 同じ値を長いランにまとめるソート順。 Parquet
  3. 1 つあたり数百万行の行グループ。 Parquet · トランスコード
