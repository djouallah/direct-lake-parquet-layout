Inside one file

A parquet file is cut horizontally into row groups, and each row group stores every column separately as a column chunk. The footer at the end describes all of it.

Click any column chunk, or the footer, to open it.

The shape of the AEMO mart in this project: 144M rows, five columns, sorted by date then time. The file stores IDs, not values; the dictionary maps them back.

Compare date with DUID: same file, same row group, one is a handful of long runs and the other is noise. The writer's row order made that difference, and of the writer's three choices (row-group size, encoding, row order) it is the only one that still affects queries once the column is in memory.

Encodings: values, or IDs into a dictionary

A column chunk stores either the values themselves (PLAIN), or a dictionary of the distinct values once plus a small integer ID per row. Sorted IDs then collapse into runs.

data page
bytes in this toy chunk

  • Dictionary encoding is smaller wherever values repeat. Measured on one real column, a 144M-row DECIMAL(18,4): 618.6 MB PLAIN against 423.1 MB dictionary-encoded.
  • It is also what Power BI can reuse. VertiPaq is itself dictionary-encoded, so a parquet dictionary can be adopted on load instead of rebuilt (Transcoding, ID swap or rebuild).
  • Writers drop it silently. Each writer has a dictionary size limit; past it, the rest of the chunk falls back to PLAIN. In this project the OSS-profile Spark writer and DuckDB's own parquet writer dropped dictionaries on the widest columns. The knob is never called the same thing: dictionary_page_size_limit (bytes) on delta-rs, DICTIONARY_SIZE_LIMIT (distinct values) on DuckDB.

The toy counts 4 bytes per value, 2 bits per ID and 2 bytes per run. Real pages add headers and compression, but the order of the four does not change.

The footer: the file's table of contents

A reader opens the footer first. It holds the schema, every row group's row count, where every chunk starts, min/max per chunk, and which encodings each chunk's pages use.

The field that matters is encoding_stats: per page type, which encoding and how many pages. It is the only structure that proves a chunk is entirely dictionary-encoded without decoding its pages, so it decides whether Power BI swaps IDs or rebuilds the column. Row groups: chosen by the writer, rarely the size you want

A writer closes a row group when it hits a row count or a byte budget, whichever comes first. Library defaults are sized for the writer's memory, not for the reader: DuckDB's is 122,880 rows. Power BI wants millions.

Two ways a row group ends up the wrong size, each seen in this project:

what happenedwhat it looked like
A library default reached OneLakeDuckDB's 122,880 rows per group: the 144M-row AEMO mart came out as 1,172 row groups instead of about 25.
A hidden byte budget wonDuckDB's Iceberg writer also closed groups at 128 MB uncompressed: on NYC taxi that is ~812,815 rows per group, 728 groups, even when a row count was asked for: the byte budget was hit first.

The rule that clears both: declare a row count in the millions, keep any byte budget comfortably above one row group, and read the footer back. What each size costs a reader is one chart on the next tab: cold against warm.

Sorting

Sorting turns values into runs

Sorted, equal values sit next to each other and a whole run is stored as one pair instead of one entry per row. Direct Lake keeps the row order of the parquet it reads, so the runs the writer built are the runs every later query scans.

runs in total

V-Order is an automatic sort. It sorts by every column at once and leads with the most repetitive, so every column that can form runs gets them, and nobody has to name a key.

A hand sort orders the columns you name. Real data repeats in combinations (the same kind of trip, over and over), so the columns you did not name stay as scattered as they arrived.

An illustration on 80 toy rows drawn from eight trip profiles. V-Order's algorithm is not published; the last button mimics the idea. On a real table: the next step.

Same rows, same engine, same four files of up to 2,097,152 rows, and the same encodings on every column. What V-Order changed is the order of the rows inside each file, and that alone took a third off the table. The columns that repeat collapse; the timestamp, which never repeats, cannot.

Measured 2026-11-11 on throwaway warehouses: CREATE TABLE … AS SELECT from the TLC file, default against ALTER DATABASE CURRENT SET VORDER = OFF, runs counted over every row of every file. The warehouse marks each file itself: tags.vorder in the Delta log and com.microsoft.parquet.vorder.enabled in the parquet footer read true on one side and false or absent on the other.

Global sort, or a sort inside each file

A global sort orders the whole table, so each value sits in one long run that crosses row groups and files. A per-file sort, which is what V-Order does, orders the rows inside each file, so every value restarts in every row group.

For compression the two land close: both are far better than arrival order.
