What the writer leaves on disk

A Delta table is a folder of parquet files plus a _delta_log that lists which ones are live. Everything a reader pays for is decided inside those parquet files.

Parquet stores a table column by column, not row by row. A query that needs two columns out of twenty reads two contiguous blocks and skips the other eighteen.

Then three decisions, all made by whoever writes the file, set what every reader pays:

  1. How many rows go in a row group. A parquet file is cut into row groups, and each holds its own slice of every column.
  2. How each column chunk is encoded. Dictionary-encoded, or plain values, and whether the footer says which.
  3. What order the rows are in. Sorted values sit next to each other and compress into runs.

None of these is a property of "parquet". Two writers given the same rows produce different files, and the next tab shows why a reader cannot undo the difference.

Inside one file

A parquet file is cut horizontally into row groups, and each row group stores every column separately as a column chunk. The footer at the end describes all of it.

Click any column chunk, or the footer, to open it.

The shape of the AEMO mart in this project: 144M rows, five columns, sorted by date then time. The file stores IDs, not values; the dictionary maps them back.

Compare date with DUID: same file, same row group, one is a handful of long runs and the other is noise. That difference was made by the writer's row order, and it is the one thing that is still paying after the data is in Power BI's memory.

Encodings: values, or IDs into a dictionary

A column chunk stores either the values themselves (PLAIN), or a dictionary of the distinct values once plus a small integer ID per row. Sorted IDs then collapse into runs.

data page
bytes in this toy chunk

Three things to take from it:

  • Dictionary encoding is smaller wherever values repeat. Measured on one real column, a 144M-row DECIMAL(18,4): 618.6 MB PLAIN against 423.1 MB dictionary-encoded.
  • It is also what Power BI can reuse. VertiPaq is itself dictionary-encoded, so a parquet dictionary can be adopted on load instead of rebuilt (Transcoding, ID swap or rebuild).
  • Writers drop it silently. Each writer has a dictionary size limit; past it, the rest of the chunk falls back to PLAIN. In this project the OSS-profile Spark writer and DuckDB's own parquet writer dropped dictionaries on the widest columns, exactly where it hurts. The knob is never called the same thing: dictionary_page_size_limit (bytes) on delta-rs, DICTIONARY_SIZE_LIMIT (distinct values) on DuckDB.

The toy counts 4 bytes per value, 2 bits per ID and 2 bytes per run. Real pages add headers and compression, but the order of the four does not change.

The footer: the file's table of contents

A reader opens the footer first. It holds the schema, every row group's row count, where every chunk starts, min/max per chunk, and which encodings each chunk's pages use. A reader can only trust what the footer declares.

one chunk's footer entry, as written by:

The field that matters is encoding_stats: per page type, which encoding and how many pages. It is the only structure that proves a chunk is entirely dictionary-encoded without decoding its pages, so it decides whether Power BI swaps IDs or rebuilds the column. Two real cases from this project, both on otherwise identical files:

  • DuckDB's writer wrote no encoding_stats until duckdb#24957; that PR measures a 142M-row string column's cold first touch at 10,857.5 ms before and 689.3 ms after.
  • delta-rs 1.6.3 and later list the dictionary page last instead of first, and the same table reads at about 5× the read CU (duckrun#84, arrow-rs#11659).

Read it yourself

Writers ignore settings without telling you; twice in this project a declared setting never reached the file and only the footer showed it. DuckDB 2.0's parquet_metadata() shows the footer, encoding_stats included:

SELECT row_group_id, row_group_num_rows, path_in_schema,
       encodings, encoding_stats, total_compressed_size
FROM parquet_metadata('abfss://<workspace>@onelake.dfs.fabric.microsoft.com/<lakehouse>/Tables/<table>/*.parquet')
ORDER BY path_in_schema, row_group_id;

Older DuckDB releases and pyarrow do not expose encoding_stats; this project's stats.py decodes the footer itself for that reason.

Row groups: chosen by the writer, rarely the size you want

A writer closes a row group when it hits a row count or a byte budget, whichever comes first. Library defaults are sized for the writer's memory, not for the reader: DuckDB's is 122,880 rows. Power BI wants millions.

Three ways a row group ends up the wrong size, each seen in this project:

what happenedwhat it looked like
A library default reached OneLakeDuckDB's 122,880 rows per group: the 144M-row AEMO mart came out as 1,172 row groups instead of about 25, and read 3.5× slower cold.
A hidden byte budget wonDuckDB's Iceberg writer also closed groups at 128 MB uncompressed: on NYC taxi that is ~812,815 rows per group, 728 groups, even when a row count was asked for: the byte budget was hit first.
The file-size cap cut a group shortdelta-rs truncates the row group in progress when the file reaches its size cap: groups written at 0.43× their declared rows, and uneven.

The rule that clears all three: declare a row count in the millions (2–6M rows per group clears both failure ends on the tables here), keep any byte budget and file cap comfortably above one row group, and read the footer back. Sorting turns values into runs

In arrival order, equal values are scattered and every row costs bits. Sorted, they sit next to each other and a whole run costs one pair.

payment_type
vendor

Three things to try. Sort by one column and watch its runs collapse to one per value. Add a second key: it gets runs too, but only inside the first key's runs. Swap the order and the winner swaps. That is the whole sort trade-off: the first column takes the best runs, later ones get what is left, and a near-unique column (a timestamp, an amount) cannot form runs at all.

The same measurement on the real NYC taxi mart, runs per 4M rows, Spark without and with V-Order:

Spark runs 31451599140 and 31450956154. The skewed categoricals collapse by three orders of magnitude, the near-unique timestamp does not move. On the 5-column AEMO mart, which has almost nothing repetitive to group, the same switch moved no column. What sorting is worth depends on the table's columns and skew, not on its row count.

Pick the key from the queries, not from the file size. One alternative key on AEMO cut the file a further 30% (543 MB against 778, four runs each) and bought no measurable query time or CU. Here 9 of 25 queries filter on the date, so the key leads with date.

Sort the table, or sort each file

A global sort keeps each value in one long run that crosses row groups. Sorting each file on its own restarts every value in every row group.

A per-file sort is still far better than arrival order, which is why V-Order works, and a sort chosen for the whole table lands in the same place: in this project duckrun's per-table sort read at 0.90× V-Ordered Spark's Direct Lake CU, the same within noise.

V-Order is these levers applied for you. Microsoft describes it as four things: a sort within each file, row-group distribution, dictionary encoding and compression. It is not a separate format; any reader can read a V-Ordered file. In Fabric Spark only the readHeavyForPBI resource profile turns it on (the default writeHeavy does not, nor does readHeavyForSpark despite its name); Fabric Warehouse has it on by default.
